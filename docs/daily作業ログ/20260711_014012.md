# 20260711_014012 Q18不安定化の原因切り分け診断（1cec020疑いをほぼ棄却）

## 目的

`docs/daily作業ログ/20260708_232156.md`で2回独立して観測された question_id=18
「東都のCTにおいて...章番号」の不安定化（旧基準では3/3 Perfect固定 → 2/3が
Incorrect寄りに）について、共通点として疑われていたコミット`1cec020`（NFC/NFD
dedup修正）との因果関係を診断する。Q27についても軽く状況を確認する。
ソースコード変更・コミットは行わない（診断のみ）。

## 結果サマリ

- **1cec020がQ18不安定化の直接原因である可能性はほぼ棄却**。コード上、
  `StructuredArtifactStore.project_names()`（1cec020の変更対象）はQ15型
  （`MilestoneThresholdListAnswerer`）と`Pipeline._resolve_project_name`の
  フォールバック（`ProjectScopedRetriever.detect_project()`がNoneを返した
  場合のみ）でしか使われない。Q18の質問文には「東都」が直接含まれており、
  `detect_project()`（1cec020と無関係な別クラスで、既にNFC正規化済み）で
  即座に案件解決されるため、Q18の検索経路は1cec020のコード変更を一度も通過しない。
- **真因は検索の不安定性ではなく生成（LLM）側のブレ**。現HEAD（`efdf6f9`）で
  N=5診断runを実施したところ、5run全てで`retrieved_sources`が完全に同一
  （契約書.docx::full_chunk1 + データサイエンティスト調査.docx::full_chunk2/1/8/22）
  だったにもかかわらず、判定はMissing/Perfect/Incorrect/Incorrect/Perfectと割れた。
  同一コンテキストからLLMが「3」「4」「見つからない」を確率的に出し分けている。
- 背景要因: 東都案件フォルダのproject-scoped BM25検索で、上位5件中4件が
  無関係な distractor文書（データサイエンティスト調査.docx＝データサイエンティスト
  収入市場調査レポート、東都の業務内容と無関係）に占有されており、正解の根拠
  （契約書.docx::full_chunk1、「3. 業務範囲」直下に「本業務の対象データ、前提
  および制約」句）はchunk1の1件のみ。distractor文書には紛らわしい見出し番号
  （chunk8「4.1 マクロな市場規模...」等）が混在しており、LLMが章番号を
  取り違えるリスクを高めている。
- 1cec020とは別の代替仮説として、同時期（07-06〜07-08）にマージされた
  `a818a76`（pptx表テキスト抽出）が東都案件自身の`提案書.pptx`に実在する
  2つの表（python-pptxで確認済み、スライド8「週次スケジュール」・スライド12
  「リスク一覧」）を新規に検索可能化しており、project-scoped BM25のコーパス
  構成（IDF統計）を変化させた時期とも一致する。ただし**未検証**（厳密なA/B
  はしていない）。
- Q27は今回のN=5でも4/5がIncorrect（同一の誤答`0.010310`を安定して出力）、
  1件がconfidenceゲートでMissingという別パターンで、1cec020適用前後
  （`vdiff2_valid`と`exp_rankfix_valid`/`diag_registry_valid`）でも同様の
  Missing優勢の挙動が一貫しており、1cec020との相関は見られない。既知の
  別問題（低confidence数値計算タイプの不安定性）として現状維持、深掘りせず。

## 学び

- `retrieved_sources`が同一コード状態内でrun間完全に決定論的であることが
  今回の切り分けの核心。「不安定」と一括りにされていたQ18の症状は、実際には
  「検索結果は決定論的に固定されているのに、そこからのLLM生成が確率的に
  ブレる」現象であり、gate_reasonだけを見ていては検索由来か生成由来かの
  区別がつかない。今後同種の不安定設問を診断する際は、まず複数runの
  `retrieved_sources`が一致するかどうかを最初に確認するのが有効な切り分け
  手順になる。
- 「両実験に共通するのは1cec020適用後という点」という07-08時点の観察は
  事実として正しいが、それは単に時系列的な相関（1cec020がマージされて
  以降のどのrunでも）であり、コード経路上の因果関係を意味しない。
  1cec020の変更範囲を実際にコードで追わないまま「唯一の共通点」を
  疑わしい原因と決め打ちすると誤った方向に工数を使うリスクがある
  （今回は幸い実装前の診断段階で気づけた）。
- 同時期にマージされた無関係なコミット（`a818a76`のpptx表抽出）が、
  対象プロジェクト自身の文書に新規テキストを追加することで
  project-scoped BM25のコーパス構成を変え、既存文書のランキングまで
  間接的に動かしうる。「変更していない文書のretrieved_sourcesが変わった」
  ケースでは、直接その文書を触った変更だけでなく、同じproject-scoped
  корpus内の他文書に対する変更（表抽出・OCR改善・復号等でテキスト量が
  増減する系のコミット）も疑う必要がある。

## 残課題

- `a818a76`（pptx表抽出）が東都project-scoped BM25のランキングを実際に
  動かしたかどうかは未検証。次に検証するなら、worktreeで`58fcc7f`
  （a818a76直前）と`a818a76`適用後の2状態でQ18の`retrieved_sources`を
  N=1で比較すれば、コーパス変化の影響だけを厳密に切り分けられる
  （1cec020は無関係と分かったので比較対象から除外してよい）。
- 生成側のブレそのものへの対策（distractor文書のランキング抑制、
  citation強制、契約書.docx::full_chunk1のみを使わせるfew-shot誘導等）は
  今回未検討・未実装（本タスクはコード変更禁止のため）。次のタスクとして
  切り出すなら「project-scoped検索で単一プロジェクトの文書点数が少なく
  かつ話題の異なる大型文書が1つ混在する場合にランキングが汚染される」
  一般化した問題として扱うのが良さそう。
- Q27はNFC/NFDと無関係の既存の別問題（低confidence数値計算タイプ、
  安定して`0.010310`という誤答を出す）と再確認したのみ。原因の深掘りは
  今回のスコープ外（別途着手）。
