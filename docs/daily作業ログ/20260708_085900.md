## やったこと

### Task 1: 白峰の契約期間抽出regexバグ修正（`47d85b3`）

`scripts/build_contract_registry.py:extract_dates()` の正規表現が「日?から」「日?まで」の
直前後にスペースを許容せず、実データのスペース入り期間表記（「2025-05-13 から 2025-07-22
まで」）で日付抽出がnullになるバグを修正。期間型・起算型の両regexに `\s*` を許容。
回帰テスト2件追加。レビューでCONFIRMED指摘なし。

### Task 2: 復号ユーティリティの配線（`2d715b5`）

`src/utils/office_crypto.py`（既存実装済み）を `build_contract_registry()` に配線。
`read_docx_text` 失敗時、ファイル名の汎用パターン `pw-<英字トークン><8桁>` から案件略号
候補と開始年月日を抽出し、`DA-[略号]-[8桁]-[拡張子]` 規則でパスワードを導出して復号→
再パースを試みる設計とした。パスワード素材の入手元は計画の論点①（ファイル名の汎用パターン）
を採用し、`project_registry.json` の `primary_alias` を補助候補として順に試行する形にした
（②のスケジュールxlsx等別ソース由来の日付候補試行は未実装、実データ検証が前提のためAブロック
へ委譲）。

レビューでCONFIRMED指摘: 復号フォールバックの `try/except` が `parse_contract_text` +
`extract_report_values` まで包んでおり、暗号化と無関係な例外（報告書解析の想定外エラー等）
まで復号経路に巻き込んで元の例外情報を握り潰していた。親エージェントが修正し、フォールバック
の適用範囲を `read_docx_text` の失敗時のみに限定した。あわせてPLAUSIBLE指摘（registry由来の
`primary_alias` が大文字化されていない）も明示的に `.upper()` して解消。

### Task 3: Q87型（APR-M1該当・完了案件・サンプル数10000行以上）の実装（`551e75e`）

`ContractCalcAnswerer` に `_answer_apr_row_threshold_list` を追加。質問文から
`APR-M(\d)` と `([0-9,]+)行以上` を汎用regexでパースし、contracts registry（status=ok）を
「完了（`final_amount_incl_tax`/`actual_hours`のいずれかが非None）×APRレベル一致
（`determine_apr_level`）×train.csv行数しきい値以上」で絞り込む。該当0件・判定不能は
Missing（ゲート厚めの原則）。

レビューでPLAUSIBLE指摘: train.csv行数取得ロジックが新設 `_project_row_count` と既存
`_answer_fixed_per_row` のインライン実装で二重管理になっていた。親エージェントが
`_answer_fixed_per_row` 側も `_project_row_count` を使うよう統一し、重複を解消。

## 学び

- 3タスクとも実装サブエージェントの一次成果物にCONFIRMED級の問題（Task 2）または
  PLAUSIBLE級の重複（Task 3）が1件ずつ出た。step-reviewの「1タスク1レビュー」運用が
  今回も手戻り防止として機能した。
- 復号フォールバックのような「例外を握り潰しうる」パターンは、フォールバック適用範囲を
  最小限（本来の失敗理由の箇所のみ）に絞ることが重要。広めのtry/exceptは意図しない経路の
  誤爆を招く。

## 追記: GitHub PR #4レビュー（`/review` + PR全体step-review）

PR作成後、`/review`（`gh pr diff`ベース）と、PR全体差分に対するstep-reviewフロー
（sonnetサブエージェント、リスク高判定＝データ抽出/ゲート/ルーティング変更のため）の
2回のレビューを実施。

### CONFIRMED（修正済み・`bca1f01`）

`pyproject.toml`に`msoffcrypto-tool`が未宣言。`scripts/build_contract_registry.py`が
このPRでトップレベル`import msoffcrypto`を追加したため、`pip install -e ".[parsers,search,dev]"`
のみのクリーン環境で`import scripts.build_contract_registry`が`ModuleNotFoundError`で
即クラッシュすることを実機（新規venv）で確認。`parsers` extraに`msoffcrypto-tool==6.0.0`を
追加して修正し、クリーン環境での479 passed・importOKを再確認済み。

### PLAUSIBLE（未修正・実データ検証待ちとしてAブロックへ）

- `read_docx_text_with_decryption`呼び出し（`build_contract_registry()`内）が
  `registry_path`を省略しているため、`project_root=tmp_path`を使う単体テストでも
  実際のリポジトリの`artifacts/project_registry.json`（本番データ）を読みに行く。
  架空案件名のため実害はない（一致しないので追加候補が増えないだけ）が、テスト分離としては
  不完全。実データ側の`project_registry.json`が更新された場合にテストの決定性が理論上
  揺らぐ余地があるため、Aブロックでの実データ検証時に`registry_path`をテスト側でも
  明示指定するよう倒すか検討する。
- `extract_dates()`の起算型regex（`日?\s*から起算して`）は「から」の直前にのみ`\s*`を
  追加しており、期間型（`日?\s*から\s*...\s*まで`）と異なり「から」と「起算して」の間の
  スペースは許容していない。白峰の実データ確認は期間型表記のみだったため今回はこの形で
  進めたが、起算型表記で同様のスペース入りパターンが実データに存在する場合は未対応。
  Aブロックの実データ検証（`contracts.jsonl`再生成）時に起算型行の抽出結果も確認すること。
