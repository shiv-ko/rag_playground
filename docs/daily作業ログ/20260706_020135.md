# 2026-07-06 実データ非依存の改善: .py未対応パーサーの追加とチャンク行境界スナップ

## 目的

このセッションはクラウド環境（`data/raw/` 無し、Anthropic/OpenAI APIキー無し）で稼働しており、
contract_rule/cross_project等のPhase 3残タスクは実データ（契約書の実際の書式）を見ずに実装すると
手戻りリスクが高いと判断（ユーザーと相談の上で合意）。代わりに、実データ非依存かつTDDで安全に
検証できる改善として、`docs/plan/2026-07-04-next-steps.md` §5「チャンク・検索の修正」の
Q28型対策に着手した。

## 結果サマリ

- `missing_triage_20260704.md` を実測ベースで再確認: valid Q4・Q28（ともにcode_staticタイプ、
  `modeling.py`参照）は「検索失敗」に分類されていたが、根本原因は`src/parsers/text_parser.py`が
  `.py`拡張子に未対応で、`.py`ファイルが常に「[未対応形式: .py]」スタブになっていたこと
  （実質的に検索対象が存在しなかった）。
- `.py`をTextParserのSUPPORTEDに追加（コミット予定）。合わせて、固定長・文字数ベースの
  `chunk_documents`（`src/parsers/chunker.py`）が行の途中でチャンクを切ることがあり、
  条件式のようなワンライナーが泣き別れて部分コードから誤断定するリスク（Q28がIncorrectになった
  疑い）があったため、分割位置を行境界（空行優先、無ければ改行）にスナップするよう変更。
- 全テスト: `.venv/bin/pytest tests/ -v` → 351 passed（新規: `tests/test_chunker.py` 5件、
  `tests/test_parsers.py` 3件追加）。
- 実データ相当のスモーク確認（`modeling.py`風の合成ファイル＋実際の質問文）で、`.py`ファイルが
  パース・インデックス・検索ヒットするまでを確認済み。

## やったこと

1. `src/parsers/text_parser.py`: `SUPPORTED`に`.py`を追加。
2. `src/parsers/chunker.py`: `_snap_end_to_line_boundary`を追加し、分割が必要な場合は
   ideal_end付近の行境界（空行優先）にスナップ。スナップ範囲はウィンドウ後半分
   （`_MIN_SNAP_RATIO=0.5`）までに限定し、改行が一切ない巨大な1行のテキストは
   従来通りハードカット（無限ループ防止のフォールバック）。
3. TDD: `tests/test_chunker.py`（新規）・`tests/test_parsers.py`（`.py`対応3件追加）を先に書き、
   red確認後に実装、全PASSまで確認。
4. step-review（sonnetサブエージェント）でレビュー: 停止性・NFC/NFD前提・既存アサーション破壊・
   二重管理ドリフト・規約違反の5観点すべて「問題なし」。停止性は数百通りのパラメータ組み合わせで
   タイムアウトが無いことも確認済みとの報告。

## 学び

- Phase 3残り（contract_rule/cross_project/パスワード保護ファイル）はversion_diffと違い、
  実データを見た前セッションが作った中間artifact（`contracts.jsonl`等）が存在しない「TODO」段階
  （`docs/data_strategy_todo.md` §7参照）。実データの無い環境でこれらを実装すると、契約書の
  実際の書式（「T&M」の表記ゆれ等）を推測することになり、規約が重視する「実データ検証済み
  ロジックのみ採用」の原則に反する。
- 一方、`missing_triage_20260704.md`のような既存の実測診断は、実データが無い環境でも
  「次に何が壊れているか」を特定する材料として十分機能した。診断記録を残しておくことの価値を再確認。
- `chunk_documents`は全ドキュメント種別に効く共通コンポーネントのため変更の影響範囲が広いが、
  「行境界スナップ・スナップ幅を後半分に制限・改行皆無時はフォールバック」という設計で
  既存の粒度・overlap感を大きく変えずに安全側の改善ができた。

## 残課題

- 今回の変更は`data/raw/`が無い環境でのユニットテスト検証止まり。実データでのvalid再実行
  （retrieval recall・N=3較正）は、data/raw・APIキーがある環境で改めて確認する必要がある。
- Phase 3 contract_rule/cross_project/パスワード保護ファイルは実データ環境での着手待ち
  （本ログの「目的」節参照）。
