# RAGコンペティション：詳細技術分析 (Deep Dive Analysis)
**〜 共有ドライブデータセットの完全解剖とRAGパイプラインの実装戦略 〜**

## Part 1: 本コンペティションの概要とRAGの必要性

### 1.1. コンペティションの背景とミッション
本コンペティション（SIGNATE「AI Engineering Challenge ～煩雑な社内ドライブをハックせよ〜」）のミッションは、架空の企業「データアステル社」の共有ドライブ内に存在する大量かつ多様な社内ドキュメントから、ユーザーの多様な質問に対して高精度で回答するシステムを構築することです。

本番データ（`data/raw/`）には、約400ファイル（総容量約225MB）のドキュメントが含まれています。

### 1.2. なぜRAGが必要なのか？
LLMには以下の制約が存在するため、単純に「すべてのドキュメントをプロンプトに入力して質問する」というアプローチは不可能です。
1.  **コンテキストウィンドウの制限とAPIコスト**: 400以上のファイルを毎回プロンプトに詰め込むと、LLMの入力上限を超過するか、天文学的なAPIコストと遅延（レイテンシ）が発生します。
2.  **ハルシネーション（幻覚）の抑制**: LLMは学習データに含まれない社内ドキュメント（データアステル社の独自規則や議事録など）について正確に回答できず、もっともらしい嘘を出力してしまいます。

これらの問題を解決するために、**RAG（Retrieval-Augmented Generation = 検索拡張生成）**を採用します。RAGシステムは、質問に関連する情報ブロックのみをドキュメント群から検索（Retrieve）し、そのコンテキストをプロンプトに追加（Augment）してLLMに推論・回答生成（Generate）を行わせます。

### 2.1. 顧客ごとの案件フォルダ（`プロジェクト/` 配下、10社）
共有ドライブ内には、金融・医療・不動産・バイオなど、業界の異なる架空の顧客企業10社のフォルダがあります。**全ての企業フォルダは、以下のように標準化された7つのサブフォルダで構成されています。**

| サブフォルダ名 | 含まれる主なファイル形式 | 主な内容とRAGにおける課題 |
| :--- | :--- | :--- |
| **`00.提案`** | `.pptx` | 顧客への提案スライド。`old`版や`final`版など**案件ごとに異なる命名規則**で新旧ファイルが混在しており、更新差分を問う質問があります。 |
| **`01.契約`** | `.docx` | 契約書。一部の契約書には**パスワード保護**が施されており、そのままでは読み込めません（復号が必要）。 |
| **`02.計画`** | `.xlsx` | プロジェクトのスケジュール表。セルの背景色（ハイライト）などの**視覚・書式情報**に依存した質問（例：「オレンジ色に塗られたタスクは何か」）があります。 |
| **`03.データ`** | `.csv`, `.xlsx`, `.md` | 分析用データセットとカラム説明。LLMにテーブル構造を理解させる必要があります。 |
| **`04.分析`** | `.py`, `.ipynb`, `.json`, `.png` | EDA（探索的データ分析）コード、モデル評価結果、およびグラフ画像。折れ線グラフや散布図画像（PNG）の数値を読み取らせる必要があります。 |
| **`05.会議`** | `.pdf`, `.docx` | 会議の議事録や打合せ資料。発言内容の要約や決定事項の推論が必要です。 |
| **`06.報告書`** | `.pptx` | 最終報告書。グラフや数表が多用されており、スライド画像とテキストの突合が必要です。 |

### 2.2. 全社共通の参照資料（`社内管理/`）
どの顧客案件にも属さない、全社共通の参照資料が格納されています。質問を処理する際の「前処理ルール」や「導出ロジック」として機能します。

*   **`社内用語集.docx`**: 社内で使われる多数の略語（例：`TG` = 目的変数, `PP` = 提案書, `FR` = 最終報告書）が定義されています。質問文に略語が含まれるため、検索前にこれを展開・置換するロジック（クエリ拡張）が有効です。
*   **`データアステル社内管理_決裁基準.md`**: 契約金額や案件ジャンル（医療は承認が1段階格上げされるなど）に基づいた決裁ルートの判定基準が記述されています。ルールベースの条件付き集計質問の根拠になります。
*   **`データアステル社内規定_パスワード導出規則.docx`**: 暗号化された契約書を開くためのパスワード生成ルール（例：`DA-[案件略号]-[契約開始日8桁]-[拡張子コード]`）が記述されています。

### 2.3. 質問の分類と要求技術
`questions_valid.csv` を分析すると、質問は単一のテキスト検索で解けるものは少なく、以下のような高度な課題解決力が要求されます。

1.  **視覚情報・メタデータの利用**: グラフ画像の数値読み取り、セルの塗りつぶし色の特定など。
2.  **複数資料・バージョン比較**: 「提案書のold版と最新版で、実質的な変更箇所はどこか」などの差分分析。
3.  **計算・推論**: 表データや決裁基準を元にした「A社の契約の合計額」や「承認者は誰になるか」といった計算・論理判断。

## Part 3: リポジトリ（`[src/](file:///Users/shiv/P/rag_comp/src)`）のアーキテクチャ

RAGパイプラインは、以下の各機能モジュールが疎結合に連携する設計となっています。

```mermaid
flowchart TD
    subgraph インデックス構築 (Build Index)
        docs[共有ドライブ資料] --> disp[ParserDispatcher]
        disp --> parsers[拡張子別パーサー群]
        parsers --> chunk[Chunker]
        chunk --> store[(Vector & Keyword Store)]
    end

    subgraph 問い合わせ・回答生成 (Query & Generate)
        query[ユーザーの質問] --> qr[HybridRetriever]
        store --> qr
        qr -->|上位 k 個のチャンク| gen[AnswerGenerator]
        gen --> cg[ConfidenceGate]
        cg -->|閾値以下なら 'わかりません'| out[最終回答]
    end
```

### 3.1. 主要モジュールの役割
*   **Orchestrator (`[pipeline.py](file:///Users/shiv/P/rag_comp/src/orchestrator/pipeline.py)`)**:
    RAG全体のコントロールタワーです。インデックス構築から、非同期並行処理による一括回答生成（`run_async`）までを管轄します。
*   **Parsers (`[parsers/](file:///Users/shiv/P/rag_comp/src/parsers/)`)**:
    *   `[dispatcher.py](file:///Users/shiv/P/rag_comp/src/parsers/dispatcher.py)`: 拡張子に応じて適切なパーサーに処理を割り振ります。また、パスから「プロジェクト名」や「カテゴリ」を自動抽出し、ドキュメントの属性（メタデータ）として紐付けます。
    *   `[chunker.py](file:///Users/shiv/P/rag_comp/src/parsers/chunker.py)`: パースされたテキストを、LLMのコンテキスト制限に収まるよう、意味のある単位（チャンク）に分割します。
*   **Retriever (`[retriever/hybrid_retriever.py](file:///Users/shiv/P/rag_comp/src/retriever/hybrid_retriever.py)`)**:
    *   **キーワード検索 (BM25)** (`[keyword_store.py](file:///Users/shiv/P/rag_comp/src/indexer/keyword_store.py)`): 正確な専門用語や型番の一致を狙います（日本語トークナイザとして unigram+bigram を使用）。
    *   **ベクトル検索** (`[vector_store.py](file:///Users/shiv/P/rag_comp/src/indexer/vector_store.py)`): 意味的な類似度で検索します。
    *   **ハイブリッド検索**: 両者のスコアを正規化し、`config.yaml` の重みに基づいて統合・再順位付け（Rerank）します。
*   **Generator (`[generator/answer_generator.py](file:///Users/shiv/P/rag_comp/src/generator/answer_generator.py)`)**:
    検索結果を整形したコンテキストと質問をプロンプトに結合し、LLMに渡して回答を生成します。
    *   `[confidence_gate.py](file:///Users/shiv/P/rag_comp/src/generator/confidence_gate.py)`: LLM自身に出力の確信度（`confidence`）を自己評価させ、設定された閾値未満の場合は「わかりません」に差し替えることで、減点ペナルティを回避します。
*   **Evaluator (`[judge.py](file:///Users/shiv/P/rag_comp/src/evaluator/judge.py)`)**:
    LLMを評価モデル（LLM-as-a-Judge）として利用し、ローカル環境で開発したシステムの回答精度を測定・集計します。

## Part 4: 高スコア獲得のための「5大技術課題」と実装戦略

コンペを勝ち抜くために、現在のスタブ（仮実装）コードを拡張し、以下の課題に対応する必要があります。

### 1. 視覚・書式情報のパース（Visual & Formatting Parsing）
*   **現状の課題**: 標準のテキストパーサーは、フォントサイズ、太字、セルの背景色といった視覚的スタイル情報をすべて削ぎ落とします。
*   **実装戦略**:
    *   `python-docx` や `openpyxl` をカスタマイズし、パース時に特定の書式情報（例：`font.bold=True` やセルの `fill.start_color`）を検出し、テキスト中にマークアップ形式（例：`**重要**` や `[Highlight: Orange] テキスト`）でインライン挿入するか、メタデータとして保持します。
    *   グラフ画像（PNG）に対しては、VLM（Vision-Language Model、例えば `gpt-4o` や `gemini-1.5-pro` など）を用いてグラフの軸ラベルや数値をOCR抽出し、それをテキストチャンクとしてインデックスに登録します。

### 2. パスワード保護ファイルの動的復号
*   **現状の課題**: パスワードで暗号化された契約書（docx）は読み込みエラーとなり、インデックス構築時にスキップされます。
*   **実装戦略**:
    *   `[データアステル社内規定_パスワード導出規則.docx](file:///Users/shiv/P/rag_comp/data/raw/share/共有ドライブ/社内管理/データアステル社内規定_パスワード導出規則.docx)` からパスワード導出ロジックを読み取り、`msoffcrypto-tool` などのライブラリを用いて、ファイルパスや契約日などのメタデータから動的に正しいパスワードを生成し、復号した上でパース処理を行います。

### 3. テーブルデータの構造保存
*   **現状の課題**: CSVやExcelシートを単純なプレーンテキストに直すと、行と列の対応関係が失われます。
*   **実装戦略**:
    *   表形式データは、Markdownテーブル形式（`| カラム1 | カラム2 |`）や HTML の `<table>` タグ形式に変換してチャンク化することで、LLMが縦横の関係性を維持したまま読解できるようにします。

### 4. 複数ドキュメント/バージョン間の比較
*   **現状の課題**: `old`版と最新版のように、類似する複数のドキュメントが検索され、コンテキスト内で情報が混ざり合って混乱します。
*   **実装戦略**:
    *   ファイル名やメタデータから「バージョン（日付や `v1`/`v2`）」を判定し、LLMに渡す前に明示的に「これは古いバージョンです」「これは最新バージョンです」といった情報をコンテキストに付与します。
    *   必要に応じて、**Agentic RAG**（LLM自身が「まず古いバージョンを検索する」→「次に新しいバージョンを検索する」→「差分を計算する」と順次実行するReActパターン）を導入します。

### 5. 数値計算・データ集計
*   **現状の課題**: LLMは四則演算やテーブルデータの集計（例：「特定の製品の売上合計」）において、しばしば計算ミスを犯します。
*   **実装戦略**:
    *   **Tool Use (Function Calling)** を導入します。LLMに直接計算させるのではなく、データ集計のための Python コード（Pandasなど）をLLMに生成させ、それをサンドボックス環境（`exec()`等）で実行して、実行結果のみを最終的な回答に組み込みます。

## Part 5: パラメータチューニングと検証戦略

システムの挙動は、`[config.yaml](file:///Users/shiv/P/rag_comp/config.yaml)` で集中管理されています。これをチューニングする際は、以下の点に注意します。

### 5.1. 評価モデルの特性理解とカスケード戦略
本番の公式評価スクリプト（`[data/raw/evaluation/crag.py](file:///Users/shiv/P/rag_comp/data/raw/evaluation/crag.py)`）は、**OpenAI API**を用いて回答を採点します。
*   **カスケード方式の検討**: 
    実行時間制限（3時間）とAPIコストのトレードオフを最適化するため、まず安価な高速モデルで処理し、`ConfidenceGate`で確信度が低かった質問のみ、より高性能な（高コストの）モデルにフォールバックして再処理するカスケードロジックを `[answer_generator.py](file:///Users/shiv/P/rag_comp/src/generator/answer_generator.py)` に組み込むことが有効です。

### 5.2. 汎化（Generalization）性能の担保
コンペの規約上、特定の企業名や特定のファイル名をハードコーディングして処理を分岐させる行為は禁止されています。
*   **対策**: 質問からメタデータ（企業名、ファイル形式、日付など）を抽出する際は、正規表現や固有表現抽出（NER）などの汎用的なロジックを用い、未知の顧客フォルダが追加されても同じコードで検索対象を絞り込めるように（メタデータフィルタリング）実装します。
