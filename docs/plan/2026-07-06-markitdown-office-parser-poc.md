# 2026-07-06 markitdown PoC検証計画（Office系パーサー抽出漏れ対策）

> 位置づけ: 本書は**PoC検証のみ**のスコープ。パイプラインへの実装・置き換えは行わない。
> 検証結果次第で、採用する場合は改めて別の実装計画書を作る。

## 1. 背景・目的

今日（2026-07-06）、`src/parsers/office_parser.py`と`scripts/build_version_diff_poc.py`の
PPTX抽出処理（自前実装、python-pptxのshapeを手動走査）に、**テーブルシェイプ内テキストを
一切拾わない**という実バグがあり、valid Q9の実害（Incorrect誤答）につながっていたことが判明・修正済み
（`docs/daily作業ログ/20260706_213550.md`）。

この経緯から、自前実装には他にも同種の抽出漏れ（グループ化シェイプ、スピーカーノート、
SmartArt、埋め込みオブジェクト等）が潜んでいる可能性を疑う。確立されたドキュメント変換ライブラリ
[microsoft/markitdown](https://github.com/microsoft/markitdown)（PDF/DOCX/XLSX/PPTX等を
Markdownへ変換、表・構造を統一的に扱う）で代替・補完できないかを評価する。

**評価軸は「精度向上に寄与するか」のみ**。今回のテーブル抽出漏れのような取りこぼしをこれ以上
自前実装のメンテナンスで潰し続けるより、実績のあるライブラリに任せた方が抜け漏れが少ないのでは
という仮説を、実データで検証する。

## 2. 検証方法

### 2.1 環境準備

- `.venv`に`markitdown`をインストールし、依存関係（`mammoth`・`pdfminer.six`・`olefile`等を
  内包する見込み）を確認する
- **ネットワーク呼び出しの有無を必ず確認**: markitdownは画像キャプション等でLLM連携オプションを
  持つ可能性がある。デフォルトで外部API呼び出しが走らないこと、または明示的に無効化できることを
  確認してから比較に進む（コンペ規約・APIコスト管理の観点）

### 2.2 比較対象ファイル

- **青嶺不動産アセットマネジメント 提案書.pptx / old版**: 今回発見したテーブル内容
  （QAレビューア欄）を基準に、markitdownが素で拾えるかを確認する第一の踏み絵
- 上記以外のPPTX数件（10案件のうち、スピーカーノート・グループ化シェイプの有無が
  分かっている/未確認のものを横断的に選ぶ）
- DOCX・XLSXも1〜2件ずつ（既存の`docx_lines`/`xlsx_lines`と比較する対象として）

### 2.3 比較観点

1. **抽出完全性**: 現行`_parse_pptx()`（修正後）/`pptx_lines()`の抽出結果 vs markitdownの
   抽出結果で、テーブル・グループ化シェイプ・ノート等の内容差分があるか
2. **出力フォーマットの互換性**: markitdownはMarkdown記法（表は`| a | b |`）で出力する。
   現行の`Document.location`（`slide_N`等、`citation_check.py`や引用検証が依存する
   位置情報）をmarkitdown出力からどう再構成するか、または再構成できないケースがあるか
3. **性能**: パース速度・依存関係の重さ（本番3時間制限、及び開発時のインストール容易性への影響）
4. **既存資産との整合**: `build_version_diff_poc.py`のdiff処理（行単位のSequenceMatcher）が
   markitdownのMarkdown出力でも同じ粒度で機能するか（表がMarkdown表記に変わることで
   diffの単位がずれないか）

### 2.4 判定基準

- 現行実装（修正後）で拾えていない実データがmarkitdownで追加に拾えるか（拾えないなら投資価値なし）
- `Document.location`相当の位置情報を保持・再構成できるか（できなければ引用検証・監査ログが壊れる）
- 依存追加のリスク（ネットワーク呼び出し・ライセンス・保守性）が許容範囲か

## 4. リスク・懸念

- **`Document.location`形式の変化**: 引用検証（`citation_check.py`）・提出診断ログ
  （`retrieved_sources`）が現行の`slide_N`/`table_idx row_idx`形式に依存しているため、
  形式が変わると波及範囲が大きい。全面置き換えは慎重に判断する
- **依存追加のコスト**: markitdownは複数ライブラリを内包するため、インストール・保守コストが増える
- **タイミング**: 締切8/20・フリーズ目安8/13を踏まえ、コアパーサーの置き換えは本PoCで
  明確な価値（現行実装では拾えない実データがある）が確認できた場合のみ着手する。
  価値が小さければ「自前実装の個別バグを都度潰す」現行方針を継続する
