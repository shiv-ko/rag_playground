## 2. 診断: スコア0.05の構造と、最初に解くべき問い

Missing 26問は一枚岩ではない。改善に着手する前に、各Missingを次の3類型に切り分ける必要がある（strategy.md §6-3）:

1. **検索の失敗** — 正解を含むチャンクがtop-kに入っていない（例: valid Q5 は最終報告書pptxの表紙スライドしか取れていない → チャンク化・検索の問題）
2. **生成の失敗** — 根拠はコンテキストにあるのにLLMが答えない/間違える
3. **較正の失敗** — 正しく答えられたのにゲートで落ちた（confidence が一律に0.0〜0.2に張り付いている疑い）、または answered すべきでないのに通過した（valid Q3、LBのIncorrect群）

現状はこの切り分けを機械的に行う手段（retrieval recall 評価）がない。**Phase 0 でこの計測基盤を先に作る**。感覚でバックログを消化しない。

3. Q6のofficial判定は表現に極端に敏感（完全一致=Perfect、区切り文字違いでMissing/Incorrect）。この判定brittlenessはLB乖離の一因になりうる
4. **local judgeはMissing誤判定だけでなくIncorrect誤判定もする**（Q25: GT完全一致の回答を「参考文書と無関係」として3/3 Incorrect化 — 検索文脈から妥当性を推測するためGT一致でも殺す）。localのIncorrect増を見たら、まずraw_answerとGTの目視 → official較正で確定。判定原則2（Incorrect増は拒否）の適用は「officialのIncorrect増」で判断する
5. **検索レイヤ（chunker/ランキング）の変更は-1製造機になりうる**（実験E）: 回収狙いの問だけでなく「現在正答している問のコンテキスト」も全て入れ替わるため、Q18型（正答→別チャンクの誤読で-1）・Q27型（数値の桁化け）が発生する。チャンク割り変更は`full_chunkN`の中身が全ファイルで変わる=影響範囲が全問。今後この層を触るなら「既存OK問のtop-5を変えない」no-harm制約を設計に含めること。また**複数変更の同居はプローブ（LLM不使用のtop-5比較）で安価にbisectできる**（今回Q27の真犯人をretrieverと特定できたのはこれ）

**残課題（優先順・2026-07-05更新）**: ①Q17/Q18のゲート通過中-1リスク ②Q6のofficial表現問題（実験Fで区切り文字が変わりofficial Incorrect→Missingに遷移。GT形式への合わせ込みは規約違反のため放置が正） ③カバレッジ攻めの再設計（no-harm制約付き。Q12は「案件名除去＋チャンク改善の合成」で取れることが実験Eで判明済み） ④pivot多dataField案件（かえで8・ひがし丘7・青潮8）で日本語指標名質問はterm_registry未接続のため発火しない — 必要になったらPipelineからstructured contextへ展開済み質問を渡す設計変更（実験F作業ログ参照） / **クローズ**: Q21型compact pivot（実験Fで回収・official Perfect）。Q0・Q10はラスタPDFで能力外と確定（`docs/pdf_highlight_feasibility.md`）

## 4. 進め方の運用ルール

1. **各フェーズ着手時に `writing-plans` で実装計画を作る**（本書はロードマップであり実装手順書ではない）。実装は `dev-process` スキルのTDDルールに従う
2. **1実験1変更**。`experiments/run_<timestamp>.json` に保存し、flip分析（Phase 0で導入）を毎回確認。「仮説→期待ゲイン→実測→採否」を記録
3. **毎実験で Incorrect ゼロ維持を最優先で確認**する。新パス追加でIncorrectが増えたら、そのパスのゲートを強化してから次へ
4. **提出は各フェーズ完了ごとに1回**（LBとローカルの乖離監視）。LBの試行回数制限を確認の上、無駄撃ちしない
5. **汎用性チェック**: すべての新ロジックに「未知の案件・ファイル・質問でも同じ方針で動くか」を自問（規約: 特定案件名・ファイル名・質問への分岐は禁止。registryは実行時にデータから構築されるので適法、の整理を維持）
