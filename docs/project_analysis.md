# プロジェクト分析ドキュメント: AI Engineering Challenge RAG

## 1. プロジェクト概要

### 1.1. 目的
このプロジェクトの最終目標は、SIGNATE AI Engineering Challenge「煩雑な社内ドライブをハックせよ」において、高精度のRAG（Retrieval-Augmented Generation）システムを構築し、高スコアを獲得することである。

### 1.2. 課題の性質
提供される社内ドライブ（多種多様なファイル群）を知識ベースとし、与えられた質問に対して正確な回答を生成する。課題は、現実世界のドキュメントが持つ以下のような複雑性を内包している。

- **多様なファイル形式**: `.docx`, `.pptx`, `.xlsx`, `.pdf`, `.csv`, `.md`, `.txt` などが混在。
- **非構造化情報**: 文章だけでなく、表、グラフ、画像などが含まれる。
- **メタ情報への依存**: ファイルの更新履歴（例: `old`版と最新版）、ファイル名、フォルダ構造自体が重要なコンテキストを持つ。
- **視覚的情報への依存**: 「黄色いハイライト」「赤字」など、書式や見た目に依存する質問が存在する。
- **保護されたファイル**: パスワードで保護されたOfficeファイルが存在する。

## 2. ディレクトリ構造と主要コンポーネント

```
/
├─── data/              # 入力データ (raw: 提供データ, sample: 開発用)
├─── docs/              # プロジェクト関連ドキュメント
├─── evaluation/        # 【重要】コンペ公式の評価スクリプト
├─── experiments/       # パイプライン実行結果 (JSON) の保存場所
├─── scripts/           # 各種実行スクリプト
├─── src/               # RAGシステムのコアロジック
└─── tests/             # テストコード
```

### 2.1. `src` ディレクトリ: RAGパイプラインの心臓部
このプロジェクトは、RAGの各機能をモジュールとして分離した、拡張性の高い設計を採用している。

- **`parsers/`**: ドキュメント解析担当。`dispatcher.py`が拡張子に応じて適切なパーサー（`office_parser.py`, `pdf_parser.py`等）を呼び出し、ドキュメントをテキストチャンクに変換する。
- **`indexer/`**: インデックス作成担当。`vector_store.py`（ベクトルDB）と`keyword_store.py`（キーワード検索用）が含まれる。
- **`retriever/`**: 検索実行担当。`hybrid_retriever.py`がベクトル検索とキーワード検索を組み合わせて、質問に関連するチャンクを取得する。
- **`generator/`**: 回答生成担当。`answer_generator.py`が、検索したチャンクをコンテキストとしてLLMに渡し、回答を生成させる。
- **`evaluator/`**: 評価担当。`judge.py`が、生成された回答の品質をLLM（デフォルトはClaude）を使って評価する。
- **`orchestrator/`**: 全体統括担当。`pipeline.py`が、上記のモジュールを連携させ、一連のRAGフローを実行する。

### 2.2. `scripts` ディレクトリ: 実行エントリーポイント
- **`run_pipeline.py`**: RAGパイプライン全体を実行し、`experiments/`に結果をJSONとして保存する。
- **`run_eval.py`**: `experiments/`に保存されたJSON結果を再集計・分析する。
- **`make_submission_file.py`**: `experiments/`のJSON結果から、提出用の`predictions.csv`を生成する。（※以前の対話で作成提案）

## 3. データ形式と処理フロー

### 3.1. 入力データ
- **ドキュメント**: `data/raw/share/` 以下に格納。上記1.2.の通り、極めて多様かつ複雑。
- **質問**: `data/raw/share/質問回答/` にあるCSV。
    - `questions_test.csv`: `index`, `question`
    - `questions_valid.csv`: `index`, `question`, `answer` (ローカル検証用)

### 3.2. 現状の実装パイプライン (`scripts/run_pipeline.py`)
1.  **Parse**: `ParserDispatcher`が全ドキュメントをテキストチャンクに分解。
2.  **Index**: `HybridRetriever`がチャンクをベクトルストアとキーワードストアに登録。
3.  **Retrieve**: ユーザーの質問に対し、`HybridRetriever`が関連チャンクを`top_k`件取得。
4.  **Generate**: `AnswerGenerator`がコンテキストと質問をプロンプトに整形し、LLM (OpenAI/Claude) に回答を生成させる。
5.  **Evaluate**: `LocalJudge` (Claude) が回答を評価し、スコアを付与。
6.  **Save**: 上記の結果全てが `experiments/` にJSONとして保存される。

## 4. 課題とボトルネック分析 (改善の方向性)

現状の実装は優れたベースラインだが、コンペで高スコアを狙うには以下の課題を克服する必要がある。AIによる実装のターゲットとなる領域である。

### 4.1. 【最重要】データパースにおける情報損失
現状のパーサーはテキスト情報しか抽出しておらず、多くの質問に回答できない根本原因となっている。

-   **ボトルネック**:
    -   **視覚情報の欠落**: 「オレンジにハイライトされたセル」「赤字の箇所」といった質問に全く対応できない。`python-pptx`, `openpyxl`, `python-docx` などのライブラリを使い、書式情報（塗りつぶし色、フォント色、太字など）をテキストと共に抽出するカスタムパーサーが必要。
    -   **表・レイアウトの崩壊**: PDFやWordの表が単なるテキストの羅列に変換され、行・列の関係が失われている。表形式を維持したまま（例: Markdown形式やHTML形式に変換して）抽出する高度なパース処理が必須。
    -   **画像・図の無視**: ドキュメント内の画像や図は完全に無視されている。質問によっては図の内容を問うものがある可能性があり、その場合は画像認識モデル（例: GPT-4oのVision機能）の導入が必要。
    -   **パスワード付きファイル**: パスワードで保護されたファイルは現在スキップされている。「パスワード導出規則」(`data/raw/share/社内管理/データアステル社内規定_パスワード導出規則.docx`) を読み解き、動的にパスワードを生成してロックを解除する機構を実装する必要がある。

-   **改善の方向性**:
    -   `src/parsers/` 内に、書式情報やテーブル構造を抽出するカスタムパーサーを開発・追加する。
    -   パスワード解除ロジックを実装し、`OfficeParser`などに組み込む。

### 4.2. 検索 (Retrieval) の非効率性
多数の無関係なファイルから情報を検索しており、精度と速度の両面で課題がある。

-   **ボトルネック**:
    -   **全ファイル検索**: 質問文に「白峰信用リスク評価株式会社の最終報告書」とファイル名が明記されていても、全ファイルを対象に検索している。これにより、ノイズの多い無関係なコンテキストがLLMに渡され、回答精度を下げている。
    -   **単純な`top_k`**: 関連度がわずかに低いが決定的に重要な情報（例: 別のファイルにある注釈）を見逃す可能性がある。

-   **改善の方向性**:
    -   **メタデータフィルタリング**: 質問文から企業名、ファイル名、文書種別などを正規表現やNER（固有表現抽出）で抽出し、検索対象を事前に絞り込むロジックを`HybridRetriever`の前段に実装する。
    -   **Rerankerの導入**: `top_k`で取得したチャンクを、より文脈理解に優れたCross-Encoderモデル（Reranker）で並べ替え、本当に重要なコンテキストだけをLLMに渡す。

### 4.3. 生成 (Generation) の限界
現在の生成ロジックは、与えられたコンテキストを要約・抜粋する以上のことができない。

-   **ボトルネック**:
    -   **複数情報源の統合・比較**: 「old版と最新版を比較したとき」のような差分比較や、複数のファイルにまたがる情報の統合ができない。
    -   **計算・推論**: 「AとBの合計は？」のような単純な計算すら、コンテキストから数値を抽出して計算するタスクは苦手。

-   **改善の方向性**:
    -   **Agentic RAG / Tool Use**: LLMに単に回答を生成させるのではなく、「思考の連鎖 (Chain-of-Thought)」を促し、複数のステップでタスクを分解させる。例えば、「1. old版の情報を検索」「2. 最新版の情報を検索」「3. 両者を比較して差分を要約」といった思考プロセスをプロンプトで誘導する。場合によっては、Pythonコードを実行するツールをLLMに与えることも有効。
    -   **質問タイプの分類**: 質問を「単純事実確認」「差分比較」「計算」「要約」などに分類し、タイプに応じた専用のプロンプトや処理フローに分岐させる。

### 4.4. 評価の二重基準
プロジェクト内のClaude評価と、コンペ公式のOpenAI評価という2つの基準が存在し、混乱を招く可能性がある。

-   **ボトルネック**:
    -   どちらのスコアを信じて改善を進めるべきか、方針が不明確。

-   **改善の方向性**:
    -   開発の初期段階では、客観的なフィードバックが得やすいClaude評価を使い、高速にイテレーションを回す。
    -   定期的に公式評価スクリプトを回し、本番スコアとの相関を確認する。特に、提出前には必ず公式評価スクリプトでのスコアを正とする。
    -   両方のスコアを`experiments/`のJSONに記録し、推移を監視する。
