# PDF内ハイライト（マーカー）抽出 実現可能性診断

> 2026-07-05、Sonnetサブエージェントによる診断（読み取り専用PoC）。レビュー済み:
> 中心主張（対象p6がテキスト0字・注釈なし・単一Image XObject）をレビュアーがpypdfで独立に再現確認。
> **レビュー時の追加発見: valid Q10の対象（蒼樹会みなみ野の最終報告.pdf）も全15ページがラスタ化**
> （全件スキャン結果 `docs/pdf_scan_results.json`）。同案件は05.会議・06.報告書のPDFが全てラスタ化
> されており、**Q0と同様Q10も「検索失敗」ではなく「能力外」に再分類**する。
> スキャナは `scripts/scan_pdf_highlight_capability.py` として保存。

対象問題（valid Q0）:
「青潮モビリティサービスの最終報告における、モビリティ需要の要因分析のページで、
マーカーされている単語をすべて抜き出してください。」
GT（検証用）: `hr、weekday、weathersit、temp`

対象ファイル:
`data/raw/share/共有ドライブ/プロジェクト/株式会社青潮モビリティサービス/06.報告書/株式会社青潮モビリティサービス_最終報告.pdf`

## 0. 利用可能なライブラリ

`.venv/bin/pip list` で確認した結果、PDF/画像関連は以下のみ:

- `pypdf==6.14.2`
- `Pillow==12.3.0`

`pdfplumber` / `PyMuPDF(fitz)` / `pdfminer.six` / OCR系（`pytesseract`, `tesseract`本体, `easyocr`等）は
**いずれも未インストール**。新規インストールは今回のタスク制約上禁止のため、この2つのみで検証した。

## 1. 対象ページの特定

`page.extract_text()`（pypdf）でPDF全13ページを走査したが、**「要因分析」「モビリティ需要」を
含むページはゼロ件**。それどころか、13ページ中12ページは`extract_text()`が空文字列を返し、
残り2ページ（p.1, p.8, p.12相当）もウォーターマーク的な短い文字列
（「株式会社 データアステル」等、11〜12文字）のみだった。

そこで各ページの `/Resources/XObject` を調べたところ、**全13ページが1280x720〜1376x768規模の
単一画像XObject（`/Image`）で全面を覆われている**ことが分かった＝各ページは実質「1枚の画像を
貼り付けただけのラスタ化ページ」（右下に "NotebookLM" のウォーターマークがあることから、
NotebookLM等でスライド生成→画像化してPDF化したものと推測される）。

画像をPillow経由で書き出し（`pages/page_01.png`〜`page_13.png`）、目視で確認したところ、
**page 6（0-indexed 5）** が「モビリティ需要の要因分析（Demand Drivers Analysis）」の図であり、
灰色のハイライトボックスが `hr`、`weekday`、`weathersit`、`temp` の4語の背後に描かれているのを
確認した（`atemp`や`workingday`など隣接する類似語はハイライトされていない）。
**これはGT「hr、weekday、weathersit、temp」と完全一致する** — 問題文・GTの妥当性は目視で裏付けられた。

ただし、この特定は **テキスト検索ではなく人間（Claudeの画像認識）による目視確認でしか成立しない**。
自動化されたページ特定手段（文字列マッチ）は本ファイルに対して機能しない。

## 2. マーカーの機械可読性判定

対象ページ（page 6）の content stream を `pypdf.generic.ContentStream` でオペレータレベルまで
分解した結果:

```
BMC / q / re [...] / W* / n / gs / g / re [...] / f*   -- ページ背景の塗り矩形
Q / EMC
BDC / q / re [...] / W* / n / cm / Do ['/Image27'] / Q / EMC   -- ページ全面を覆う画像1枚
BDC / q / re [...] / W* / n / g / re [1180, 6, 96, 24] / f* / Q / EMC  -- 右下の小さな塗り矩形（ウォーターマーク背景と推定）
```

**text-showing オペレータ（`Tj` / `TJ` / `'` / `"`）は1件も存在しない。**
すなわち:

- (a) `/Annots` に `/Highlight` 注釈は **存在しない**（対象ページ・全13ページとも0件）。
- (b) ハイライトが「文字の背後の塗り矩形」として入っているという構造も**存在しない**
  （そもそも文字がベクタとして描画されていない）。
- (c) **該当**: マーカーを含む図全体が画像化されており、`hr`/`weekday`/`weathersit`/`temp`の
  文字とその背後の灰色ボックスは、すべて埋め込み画像のピクセルとしてのみ存在する。

### 判定: 機械可読ではない（case c）

pypdf/Pillowだけでは、ハイライトされた単語列をプログラム的に再現する手段がない。
理論的には以下のいずれかがあれば可能:

- OCR（`pytesseract`+Tesseract本体、または`PyMuPDF`+外部OCR、EasyOCR等）で画像から文字認識し、
  かつ背景色（グレー系ハイライト）の画素を単語のバウンディングボックスと突き合わせて
  「ハイライトされている単語だけ」を判別するロジック
- 上記いずれも本環境には未導入で、今回は新規インストール禁止のため検証不可

## 3. PoCスクリプトの実行結果

`poc_pdf_highlight_extraction.py`（scratchpad）を作成し、3段階フォールバックで検証:

```
[Step1] text-search page match: None   -> 失敗（本文にマッチする語が皆無）
[Step2] /Highlight annotations on target page: 0   -> 失敗
[Step3] vector rect+text co-occurrence: has_fill_rect=True, has_text_op=False, text_op_count=0
[Verdict] ページ全体がラスタ画像。pypdf/Pillowのみでは単語列を機械的に再現できない。
extracted_words=[]
GT_words=['hr', 'temp', 'weathersit', 'weekday']
match=False
```

**PoC結果: 抽出失敗（0語）。** ただし目視では対象ページ特定とGT一致を確認済み
（上記セクション1参照）。つまり「問題は正しく作問されているが、現行の利用可能ツールセットでは
機械的に解けない」という結論になる。

## 4. 一般化の検証（適用範囲の集計）

`data/raw/share/共有ドライブ` 配下の全PDF **28件** を走査（`scan_all_pdfs.py`、日本語パスは
NFC正規化して比較 — 実測では本ファイルシステム上のパスは既にNFC形式で、NFD起因の不一致は
今回は検出されなかったが、移植性のため正規化コードは残している）。

集計結果:

| 指標 | 件数 / 28件中 |
|---|---|
| `/Highlight`注釈を持つPDF | **0件** |
| 何らかの抽出可能テキストを持つページがあるPDF | 10件 |
| 全ページがラスタ画像化（抽出テキスト実質ゼロ）のPDF | **18件（64%）** |
| 「塗り矩形+文字描画オペレータ共存」ヒューリスティック該当PDF | 12件 |

補足: 4つ目の「塗り矩形+文字描画共存」は**弱いヒューリスティック**（ページ内に矩形塗りつぶしと
文字描画が両方存在する、という粗い共起判定のみで、矩形と文字の座標が重なっているかは見ていない）。
実際に該当PDF（例:「株式会社青葉バイオメディカル機器/提案書.pdf」「医療法人社団蒼泉会 ひがし丘総合病院_最終報告.pdf」等）
を確認すると、ヒットの正体はテーブル罫線・装飾枠・ウォーターマーク背景などであり、
**「特定の単語の背後だけに置かれた強調矩形（本物のマーカー）」に該当する例は見つからなかった**。
青潮モビリティサービスのファイル自体も、この粗いヒューリスティックには「該当ページ3件」として
引っかかるが、実体はウォーターマークの文字＋別の装飾矩形の共起であり、偽陽性である
（Step3で確認した通り、真の対象ページでは`text_op_count=0`）。

**結論: 現在のデータセットには、PDFのネイティブ機構（注釈 or ベクタ矩形）によるハイライトを
機械的に読み取れる例は1件も確認できなかった。** 青潮モビリティサービスの案件は、全PDF中でも
最も典型的な「スライド画像をPDF化しただけ」のパターン（18/28件、64%）に属する。

## 5. 一般実装の設計案（実現した場合）

もし将来OCR系ライブラリの導入が許可された場合の設計案（今回は未実装）:

- **スキーマ**: 既存の`artifacts/office_marks.jsonl`と同じ形（`source_path`, `project_name`,
  `section`, `file_name`, `extension`, `unit_type`, `text`, `highlight_color`等）に、
  PDF由来のレコードとして `unit_type: "pdf_ocr_highlight"`, `page_number`, `bbox` を追加する形で
  ロー単位追記するのが、既存の構造化パス（`src/retriever/structured_context.py`の
  `build_office_style_context` / `StructuredArtifactStore.office_marks_for`）への最短接続になる
  （`_highlight_color_name`や色名判定ロジックがそのまま流用できるため）。
- **生成スクリプト**: `scripts/extract_office_marks.py`はdocx/pptxのpython-docx/python-pptx
  APIに強く依存した実装であり、PDFのOCR＋画像処理パイプラインとは処理系列が全く異なる
  （ページラスタ化→OCR→色マスク→単語とのバウンディングボックス突き合わせ）。よって
  **既存スクリプトの拡張ではなく新規スクリプト（例: `scripts/extract_pdf_highlight_marks.py`）
  として追加し、出力は同じ`artifacts/office_marks.jsonl`にマージ（もしくは別ファイル
  `artifacts/pdf_highlight_marks.jsonl`にして`StructuredArtifactStore`側で両方読み込む）**
  のが筋が良い。
- **処理フロー（案）**: (1) PyMuPDF等でページを画像化 → (2) OCR（Tesseract等、日本語+英数字混在
  対応が必要）で単語とbboxを取得 → (3) 背景色サンプリングでハイライト色領域を検出 → (4) 単語bboxと
  ハイライト領域の重なり率で「マーカーされた単語」を判定。
- **必要な追加パッケージ**: `PyMuPDF`（高解像度ラスタ化に強い。pypdfの`page.images`は埋め込み画像
  そのものの解像度に依存し将来的な最適化余地は小さい）、OCRエンジン
  （`pytesseract`+Tesseract本体、または`easyocr`）。いずれも現環境には未導入。

## 6. 推奨

**今回の質問（青潮モビリティサービス案件）およびデータセット全体を見る限り、PDFハイライト抽出の
「能力外ゲート」は維持すべき。** 根拠:

1. 対象PDFの該当ページはテキスト描画オペレータを一切持たない完全ラスタページであり、
   `pypdf`/`Pillow`のみでは原理的に単語列を再現できない（OCRが必須）。
2. OCR系ライブラリは現環境に未導入であり、今回のタスク制約下でも新規インストールは禁止。
   仮に導入が許可されても、日本語混在レイアウト＋色マスクという実装コストの高い新規パイプラインが
   必要で、既存の`extract_office_marks.py`拡張では済まない。
3. 一般化調査でも、28件のPDF中**注釈ベースのハイライトは0件**、**ページ全体ラスタ化が18件（64%）**
  であり、たとえOCRパイプラインを実装しても投資対効果（対応できる案件数）が低い。
4. 目視では対象ページとGTの一致を確認できたため、問題設定自体は妥当である
  （＝「解けるはずなのに実装が甘い」ではなく「現行ツールセットの外側にある」タイプの限界）。

よって、この問題については無理に部分点を狙う実装をせず、**能力外（PDF画像内マーカーは検出不可）
として明示的にスキップ/ゲートする方針を維持するのが妥当**と判断する。
