# データセット概要

SIGNATE「AI Engineering Challenge ～煩雑な社内ドライブをハックせよ～」の本番データ。架空企業「データアステル社」の案件資料一式を模した、複数業界・複数案件にまたがるマルチモーダルなコーパス。`data/raw/` に展開済み。

## 1. ディレクトリ構成

```
data/
├── raw/                          # 本番データ（展開済み）
│   ├── share/                    # share.zip の中身
│   │   ├── 共有ドライブ/          # 検索対象コーパス本体
│   │   │   ├── プロジェクト/       # 案件フォルダ（10社）
│   │   │   └── 社内管理/          # 社内規定・用語集など全案件共通の参照資料
│   │   └── 質問回答/
│   │       ├── questions_valid.csv  # 30問（正解付き・ローカル検証用）
│   │       └── questions_test.csv   # 100問（正解なし・本番回答対象）
│   ├── evaluation/               # evaluation.zip の中身（評価コード一式）
│   ├── 配布データ/predictions.csv  # 提出サンプル（配布データ側のコピー）
│   └── tutorial.ipynb
└── sample/                       # 本番データ公開前に使っていたダミーデータ（無関係・退避用）
```

`data/sample/` は本番データとは無関係な社内文書もどきのモックで、`questions.json` に10問のQ&Aが入っている。パイプラインの配線確認用に作った暫定データなので、本番では `data/raw/` 側のみを対象にする。

## 2. 共有ドライブ（検索対象コーパス）

### 2.1 案件フォルダ（`プロジェクト/`、10社）

金融・不動産・人材・医療・モビリティ・バイオメディカルなど業界の異なる架空企業10社。**全社共通で同じサブフォルダ構成**を持つ。

| フォルダ | 内容 |
|---|---|
| `00.提案` | 提案書（pptx）。改訂版が `_v1`/`final` や `old`/無印など**社ごとに命名規則が異なる** |
| `01.契約` | 契約書（docx）。一部は**パスワード保護**（§2.3参照） |
| `02.計画` | スケジュール（xlsx） |
| `03.データ` | `train.csv`/`train.xlsx`、カラム説明.md |
| `04.分析` | `analysis_outputs/`（metrics.json, leaderboard.csv）と `analysis_project/`（EDA notebook、features/modeling/preprocess/infer等のPythonコード一式、`reports/figures/` 配下にグラフPNG） |
| `05.会議` | 会議録（pdf/docx）、報告資料（pdf/docx）。日付ごとに複数回分 |
| `06.報告書` | 最終報告書（pptx）。`_old` 版が併存する案件あり（新旧比較を問う設問に対応） |

企業により保有ファイルの厚み・形式（pdf vs docx、csv vs xlsx併存、old版notebookの有無など）が異なるため、**汎用的なファイル形式別パーサ**が必須。

### 2.2 社内管理フォルダ（`社内管理/`、全案件共通の参照資料）

| ファイル | 内容 | 重要度 |
|---|---|---|
| `社内用語集.docx` | 文書種別・会議進行・契約請求・データ分析に関する社内略語辞典（例: PP=提案書, FR=最終報告書, TM=time_and_materials, TG=目的変数, APR-M2=部長承認 など多数） | ★★★ 設問に社内用語が出るため展開ロジック必須 |
| `データアステル社内管理_決裁基準.md` | 契約金額帯ごとの承認レベル（主任〜本部長）。医療案件は1段階格上げ、time_and_materials契約は部長承認以上、の優先順位ルールあり | ★★★ 条件分岐を伴う集計設問の根拠になりうる |
| `データアステル社内規定_パスワード導出規則.docx` | 保護ファイルのパスワードを `DA-[案件略号]-[契約開始日8桁]-[拡張子コード]` の形式で導出する規則 | ★★☆ パスワード付きファイルの復号に必要 |
| `座席表.pptx` | 座席表 | 参照頻度は低いと想定 |

### 2.3 パスワード保護ファイル

例: `01.契約/契約書_pw-kaede20250902.docx`。`社内用語集`の案件略号と`パスワード導出規則`を組み合わせて機械的に復号できる設計になっている（ハードコード禁止のため、実行時に規則から導出する処理が必要）。

## 3. 質問回答（`質問回答/`）

| ファイル | 件数 | 正解列 | 用途 |
|---|---|---|---|
| `questions_valid.csv` | 30 | あり | ローカルでのCRAG評価・パイプライン検証用 |
| `questions_test.csv` | 100 | なし | 本番の回答生成対象。`predictions.csv` として提出 |

設問例（`questions_valid.csv` より）:
- 「青潮モビリティサービスの最終報告における、モビリティ需要の要因分析のページで、マーカーされている単語をすべて抜き出してください。」→ `hr、weekday、weathersit、temp`（画像内テキストの読み取りが必要）
- 「KSSのfigure_06.pngにおいて、dayによる件数推移とあわせて表示されているTG平均が最も低い日は何日ですか。」→ `20日`（グラフ画像の読み取り＋社内略語TGの理解が必要）

`questions_test.csv` には新旧資料比較系の設問も含まれる（例:「提案書old.pptxから提案書.pptxへの更新内容のうち、案件遂行に関連する実質的な変更を挙げてください。」）。単一資料の読解に留まらず、**複数資料・複数案件をまたぐ検索/照合/集計**が要求される設問がある。

## 5. evaluation フォルダ（評価コード）

```
evaluation/
├── crag.py              # 評価実行エントリポイント
├── readme.md            # 評価方法の説明（後述docs/submission.md参照）
├── Dockerfile / docker-compose.yml
├── data/valid_txt.csv   # 模範解答サンプル（index, answerのヘッダーなしcsv）
├── submit/predictions.csv  # 提出サンプル（全問「わかりません」のダミー）
└── src/
    ├── settings.py      # フォーマット定義（max_num_tokens=1000等）
    ├── validator.py     # 提出ファイルのバリデーション
    ├── dbmanager.py     # 模範解答ロード・結果保存
    └── evaluator.py     # CRAGによるLLM採点ロジック（数値/要素列挙問題は個別ルールあり）
```

デフォルトの評価モデルは `gpt-5.2-2025-12-11`、`--max-num-tokens 1000` が既定値（コンペ制約と一致）。

## 6. RAGパイプライン設計上の要点

- **多様な資料形式**（pptx/docx/xlsx/pdf/画像/コード/Notebook）を横断的にパース・チャンク化する必要がある
- **社内用語集の展開**をクエリ前処理または検索対象への組み込みとして実装する必要がある（例: TG→目的変数）
- **決裁基準・パスワード導出規則のような「ルール文書」**は、単純な検索対象であると同時に、条件付き集計・復号処理のロジック源にもなる
- **画像・グラフの読み取り**（マーカー語句抽出、折れ線グラフの数値読み取り等）が必須 → OCR/VLM対応が前提
- **新旧版ファイルの命名規則が案件ごとに異なる**（`_v1`/`final`、`old`/無印など）ため、バージョン比較設問には表記ゆれに頑健な突合ロジックが必要
- ハードコード（案件名・質問文に応じた個別分岐）は禁止されており、未知の案件・資料・質問に対しても同じ処理方針で汎用的に動作する実装が求められる
