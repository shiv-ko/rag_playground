# 勝つための戦略マップ

このドキュメントはコンペで勝つための**上位の戦略地図**。抽象レイヤーの方針・実験の全体像を扱う。ベースライン構築までの作業記録は [`todo_and_experiments_baseline.md`](./todo_and_experiments_baseline.md)、ベースライン後の実行ロードマップは [`plan/plan_0703.md`](./plan/plan_0703.md)、データ基盤の詳細は [`data_strategy_todo.md`](./data_strategy_todo.md) で管理する。前提知識は [`dataset_overview.md`](./dataset_overview.md)・[`submission.md`](./submission.md) を参照。

## 1. スコアの構造と勝ち筋

### 1.1 スコアの分解

最終スコア = 全100問の平均。各問は Perfect(+1) / Acceptable(+0.5) / Missing(0) / Incorrect(-1)。

```
スコア ≈ (回答した問題の正答率 × 回答カバレッジ) − (誤答率 × 回答カバレッジ)
```

つまりレバーは2つしかない:

1. **能力の拡張** — 正しく答えられる設問タイプを増やす（攻め）
2. **較正の精度** — 「答えるべきか、わかりませんと言うべきか」の判断を正確にする（守り）

### 1.2 CRAGの非対称性が戦略の根幹

- **Incorrect 1問 = Perfect 2問分の損失**。確信のない回答は出さないほうが期待値が高い
- **数値問題**: 完全一致のみPerfect。四捨五入一致でAcceptable。惜しい数字はむしろ危険
- **要素列挙問題**: 部分一致はすべてIncorrect（Acceptableなし）。**全要素読み取れる確信がなければMissingに逃がすべき最危険カテゴリ**
- 帰結: 設問タイプごとに「攻める/守る」の損益分岐が異なる。一律の確信度閾値では最適化できない

### 1.3 理論上限で意思決定する

- valid/test全130問の能力別分類（→ [`question_labels.csv`](./question_labels.csv)、作成済み）から「現在のパイプラインで正答可能な問題数」= 理論上限を常に把握する
- 各実験の価値 = **該当設問数 × 改善確率 × 1問あたり得点差**。着手前にこの見積もりを立て、実測で更新する
- 「上限に届いていないのに能力を追加する」のは無駄。まず既存能力の取りこぼし（検索ミス・生成ミス）を潰す

## 2. 守り: Incorrectをゼロに近づける

守りは攻めより**常に先行**させる。新能力の追加はIncorrectのリスク源も増やすため、ゲートが固まっていない状態での能力追加はスコアを下げうる。

### 2.1 多層の確信度設計

| 層 | 検出したい失敗 | 手段の例 |
|---|---|---|
| 検索段階 | 該当文書が見つかっていない | 検索スコアの下限、案件検出の失敗判定 |
| 生成段階 | 根拠なしで答えている | 根拠チャンクの引用強制、引用実在の機械チェック |
| 出力段階 | もっともらしい誤答 | self-consistency（複数回生成の一致判定）、自己検証プロンプト |
| タイプ別 | カテゴリ固有のリスク | 要素列挙・数値問題は閾値を引き上げ |

### 2.2 実験候補（抽象）

- 確信度スコアの設計そのもの（検索スコア由来 / LLM自己申告 / 両者の合成）
- `confidence_threshold` の設問タイプ別チューニング
- 「わかりません」がevaluatorに確実にMissing判定される表現の確認（`evaluation/src/evaluator.py` の判定ロジックを読む）
- Incorrect事例の類型化を毎実験で継続し、ハルシネーション誘発パターン（誤検索、他案件混入、数値の丸め、列挙の取りこぼし）を蓄積する

## 3. 攻め: Perfectを増やす

### 3.1 設問タイプ別・能力マップ（設問数は `question_labels.csv` のprimary_type実測、2026-07-03時点）

| 設問タイプ | 必要能力 | test | valid | 対応フェーズ（plan_0703） |
|---|---|---:|---:|---|
| Excel表示状態（ハイライト・Pivot・フィルター） | spreadsheet構造化抽出 | 21 | 3 | Phase 2 |
| 新旧版の比較 | 表記ゆれ頑健なdiff＋意味分類 | 11 | 1 | Phase 3 |
| 社内用語・略号の解決 | 用語集展開（term_registry） | 11 | 4 | Phase 1 |
| 契約ルール・条件計算 | 契約構造化＋プログラム計算 | 10 | 3 | Phase 3 |
| Office書式（太字・ハイライト等） | 書式抽出（office_marks） | 9 | 3 | Phase 2 |
| 表データ集計 | NL→pandas計算 | 9 | 3 | Phase 2 |
| 複数案件の横断/集計 | 横断テーブル＋表集計 | 9 | 1 | Phase 3 |
| 単一文書のテキスト読解 | 検索精度・チャンク設計 | 6 | 4 | Phase 1 |
| 要素列挙 | 抽出完了性ゲート | 4 | 2 | Phase 1〜2 |
| 分析成果物（metrics/NB/コード） | analysis_registry統合 | 7 | 5 | Phase 4 |
| 画像・グラフ読み取り | VLM | 2 | 1 | Phase 4 |
| パスワード保護ファイル | 規則からの機械的導出 | (2ファイル) | - | Phase 3 |

優先順位はこの実測分布に基づく。secondary_typesを含めると各行の実効問数はさらに増える（特にlist_extraction・internal_terms・numeric_exactは多くの設問のsecondaryに付く）。

### 3.2 検索精度（すべてのタイプの土台）

- 案件フォルダ絞り込みの精度（略号対応を含む）
- ハイブリッド検索（BM25 + ベクトル）とリランキング
- チャンク設計（サイズ・オーバーラップ・文書構造の保持・メタデータ付与）
- クエリ拡張・書き換え（用語集展開はここに含まれる）
- 評価方法: 生成を通さず「正解の根拠チャンクがtop-kに入るか」の検索単体評価（retrieval recall）を持つと、失敗の切り分けが速い

### 3.3 生成精度

- プロンプト設計: CRAG基準の埋め込み、出力フォーマット制御（数値だけ簡潔に答える、模範解答の単位・粒度に合わせる）
- コンテキスト量の最適化: チャンクを何件入れるか、long-context に寄せるか検索で絞るか
- 1000トークン制約は上限であって目標ではない。簡潔な回答のほうがjudgeの誤判定も減る

### 3.4 構造化抽出（最大の未開拓領域）

当初はマルチモーダル（VLM）を最大の未開拓領域と見込んでいたが、設問ラベリングの実測（§3.1）で覆った: image_graphがprimaryの設問はtestでわずか2問、一方Excel表示状態・Office書式・表集計の合計は39問。**最大の投資先は、`data_strategy/` で構築済みの構造化抽出資産（spreadsheet_cells / office_marks / version_pairs / 各registry）を回答パイプラインに接続すること**である。詳細は [`data_strategy/README.md`](./data_strategy/README.md) と [`plan/plan_0703.md`](./plan/plan_0703.md) Phase 2〜3。

VLMは優先度を下げて維持する。実装する場合は2つの方式があり、コスト・精度のトレードオフを実験で決める:

1. **インデックス時キャプション化**: 全画像をVLMで事前にテキスト化して索引に入れる（検索可能になるが事前コスト大、質問に依らない汎用キャプションでは細部が落ちる）
2. **クエリ時画像参照**: 検索で画像ファイルを特定し、回答生成時に画像を直接VLMに渡す（細部読み取りに強いが、画像を検索でヒットさせる工夫が別途必要——ファイル名・周辺文書からの間接検索）

グラフ数値読み取りのような細部依存の設問には方式2（またはハイブリッド）が必要になる可能性が高い（マーカー・ハイライト抽出は当初VLM案件と見ていたが、office_marks/spreadsheet_cellsの書式抽出で対応する）。ただし該当問数が少ないため、期待値に見合う工数でのみ実装する。

## 4. 横断基盤

### 4.1 評価の信頼性

- ローカルjudge（Claude）と本番judge（gpt-5.2）の較正を早期に1回行い、乖離の傾向を把握する
- **valid 30問は少ない**。1問 = 約3.3%の分散があるため、±1問の変動で一喜一憂しない。設問タイプ別の内訳で見る
- valid 30問への過剰適合に注意（本番100問とは分布が異なりうる）。「validで効いた理由」が汎用的に説明できる変更のみ採用する
- 実験間の**flip分析**（どの問題が改善し、どの問題が悪化したか）を標準の確認項目にする

### 4.2 実験運用

- 1実験1変更の原則。`experiments/run_<timestamp>.json` に保存し `run_eval.py` で集計（既存運用どおり）
- パース・インデックスの結果をキャッシュし、実験サイクル（変更→30問評価）を数分オーダーに保つ。**サイクル速度が実験回数を決め、実験回数がスコアを決める**
- 各実験は「仮説→期待ゲイン見積もり→実測→採否と理由」を記録する

### 4.3 時間・コスト予算

- 本番の3時間制限: 100問の逐次処理で間に合うかをベースラインで実測し、必要なら並列化・キャッシュ・モデル使い分け（軽量モデルで下処理、上位モデルで生成）を導入
- API費用と実験回数のバランス: 30問評価1回あたりのコストを把握しておく

## 5. リスク管理

- **規約遵守**: 特定の案件名・質問・ファイル名への個別分岐は禁止。すべてのロジックに「未知の案件・資料・質問が来ても同じ方針で動くか」の汎用性チェックを通す（案件リストのフォルダ由来導出はその一例）
- **提出戦略**: 初回提出済み（2026-07-03、LB -0.06666 / ローカルvalid 0.05）。以降はフェーズ完了ごとに提出し、ローカルスコアとLBスコアの乖離を監視する。LBが負＝testでゲートを通過したIncorrectが存在することを意味し、守りの再設計（plan_0703 Phase 1）の根拠
- **再現性**: 本番judgeは1回のみ・シード固定。自分のパイプラインも温度・シードを固定し、同一入力で同一出力を保証する
- **終盤フリーズ**: 締切前の最終期間は新機能を凍結し、安定化・エッジケース処理・最終検証に振る

## 6. 優先順位の原則（まとめ）

1. 守り（ゲート・較正）は攻め（能力追加）より先
2. 実験の価値 = 該当設問数 × 改善確率 × 得点差。valid分類でこの見積もりを持ってから着手
3. 検索単体評価を持ち、失敗を「検索の失敗 / 生成の失敗 / 較正の失敗」に切り分けてから対策する
4. 実験サイクルの速さ自体に投資する（キャッシュ・自動集計・flip分析）
5. validへの過剰適合を避け、汎用的に説明できる改善のみ本採用
