# step-review: コミット前の都度レビュー

実装→全テストPASS→**コミットの直前**に、そのタスクのdiffだけをレビュー用サブエージェントに見せ、 確実な問題（CONFIRMED）だけ直してからコミットする。レビューは1タスク1回、対象はそのタスクのdiffのみ （リポジトリ全体を見せない。安く・速く・毎回やることが目的）。

## フロー（dev-processのTDDに1ステップ挿入する）

1. dev-processの手順で実装し、`.venv/bin/pytest tests/ -v` 全件PASSまで到達する
2. `git add`する前に、レビューエージェントを起動する:
   - 通常の変更 → **model: gpt-5.4-mini**
   - リスクの高い変更（パイプラインの分岐・ゲート・提出経路・データ抽出）→ **gpt-5.4以上**に上げる
3. レビュー結果のうち **CONFIRMED（file:line付きの確実な問題）だけ**修正する。スタイル指摘・好みは無視
4. 修正したら再度全テストPASS→コミット。レビューで判断が割れた指摘は握りつぶさず
   `docs/daily作業ログ/` の当該ブロックのログ（`YYYYMMDD_HHMMSS.md`）にメモする（vault.mdではない）

## レビューエージェントへの依頼テンプレート

Agentツール（subagent_type: "general-purpose"、**model はフロー手順2の判定で決める**: 通常=gpt-5.4-mini / リスク高=gpt-5.4以上）に以下を渡す。 diffは親が貼らず、エージェント自身に `git diff`（未コミット分）を実行させる:

```
あなたは /Users/shiv/P/rag_comp（RAGコンペ）のコードレビュアーです。
`git diff` と `git diff --cached` で未コミットの変更を確認し、以下の観点で確実な問題だけを報告してください。

【タスクの意図】<1〜2文で今回の変更の目的>

【確認観点 — このリポジトリで実際に起きた事故パターン】
1. 分岐の排他ミス: elifで片方のパスが構造的に死んでいないか。条件が常にTrue/Falseのデッドコードがないか
2. 実データ前提の欠落: パス・案件名・日本語の文字列比較にNFC/NFD正規化が必要な箇所はないか。
   テストの合成データが実データの形式（列名ゆれ・番号接頭辞・「A / B」複合値・ヘッダ残骸行）を反映しているか
3. 既存アサーションの意図破壊: 既存テストのアサーションを変更している場合、それは「バグ修正」か
   「元の制約（例: APIがtemperatureを受け付けない）の破壊」か。元のアサーションには理由がある前提で疑う
4. 二重管理ドリフト: 同じ構成・引数・ロジックが複数ファイルにあり（例: run_pipeline.pyとmake_predictions.py）、
   片方だけ変更していないか
5. 競技規約違反: 特定の案件名・ファイル名・質問文・正解のハードコードがないか。
   question_labels.csv（人手ラベル）を回答生成パスからimportしていないか

【出力形式】
- CONFIRMED の問題のみ、file:line と「何が・どう壊れるか」を1件ずつ
- 推測レベルは PLAUSIBLE として分けて短く
- 問題なければ「問題なし」と一言。スタイル・好みの指摘は書かない
```

## 運用ルール

- **1タスク=1レビュー=1コミット**。レビューを溜めない（溜めると今回のNFDバグのように統合後まで潜伏する）
- レビューが「実データでの動作が不明」と指摘したら、コミット前に実データスモーク （artifacts/実ファイルでの少数件確認）を追加で行う — ユニットテスト全PASSは実データで動く証明にならない
- レビュー結果への反論は自由（誤検知は普通にある）。ただし観点3（既存アサーションの意図）の指摘だけは 必ずgit履歴か人間への確認で裏を取ってから上書きする
- サブエージェントが使えない環境（Codex等）では、同じテンプレートを自分への セルフレビューチェックリストとしてコミット前に1周する
