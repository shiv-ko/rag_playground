# `docs/strategy.md` 初学者向け解説

この文書は、`docs/strategy.md` の内容を、RAGコンペに初めて参加する人にもわかるように噛み砕いた説明です。元の文書は「どうすればスコアを上げられるか」を短く整理した戦略マップです。ここでは、なぜその戦略になるのか、何を優先すべきなのかを順番に説明します。

## まず、このコンペで何をしているのか

このコンペでは、社内資料のようなファイル群をもとに、質問へ回答するRAGパイプラインを作ります。RAGとは、ざっくり言うと次の流れです。

1. 質問を読む
2. 関係ありそうな資料を探す
3. 見つけた資料を根拠に回答を作る
4. 自信がなければ「わかりません」と答える

重要なのは、ただたくさん答えればよいわけではない点です。間違った回答には大きなペナルティがあります。そのため、この戦略では「正しく答えられる問題を増やす」ことと同じくらい、「危ない問題では答えない」ことを重視しています。

## 1. スコアの仕組み

各問題の評価は次の4種類です。

| 評価 | 点数 | 意味 |
|---|---:|---|
| Perfect | +1 | 完全に正しい |
| Acceptable | +0.5 | だいたい正しい |
| Missing | 0 | わからない、と答えた |
| Incorrect | -1 | 間違った答えを出した |

ここで一番大事なのは、Incorrect が -1 点であることです。Perfect 1問分を消すだけでなく、Missing にしておけば 0 点で済んだ問題を -1 点にしてしまいます。

たとえば、10問中5問に正解して、5問を Missing にすれば合計は +5 点です。一方、5問に正解して、5問を間違えると合計は 0 点です。答えた数は同じでも、間違いが多いと一気に不利になります。

そのため、スコアを上げる方法は大きく2つです。

1. 正しく答えられる問題の種類を増やす
2. 間違えそうな問題を見抜いて Missing に逃がす

元文書では、前者を「攻め」、後者を「守り」と呼んでいます。

## 2. なぜ守りが重要なのか

このコンペでは、間違いの損失が大きいので、守りを先に固める必要があります。

特に危険な問題があります。

| 問題タイプ | 危険な理由 |
|---|---|
| 数値問題 | 完全一致が求められることが多く、少し違う数字が危険 |
| 要素列挙問題 | 必要な要素を一部だけ書くと Incorrect になりやすい |
| 複数資料をまたぐ問題 | 別案件や別ファイルの情報を混ぜやすい |
| 書式・表示状態の問題 | 通常のテキスト検索だけでは見えない情報がある |

たとえば「該当する項目をすべて答えてください」という問題で、5個あるうち4個だけ答えると、部分点ではなく Incorrect になる可能性があります。この場合、全部そろっている確信がなければ Missing にしたほうが期待値は高くなります。

## 3. 確信度とは何か

確信度とは、「この回答を出してよいか」を判断するための材料です。単にLLMに「自信がありますか」と聞くだけでは不十分です。元文書では、複数の層でチェックする方針を立てています。

### 検索段階のチェック

まず、そもそも正しい資料が見つかっているかを確認します。質問に関係する文書が検索結果に入っていなければ、どれだけ上手に回答を生成しても正解できません。

見るべき例は次の通りです。

- 検索スコアが低すぎないか
- 質問に出てくる案件やファイルが特定できているか
- 略称や社内用語を展開できているか

### 生成段階のチェック

次に、回答が根拠にもとづいているかを見ます。LLMは、資料に書かれていないことでも自然な文章で答えてしまうことがあります。これをハルシネーションと呼びます。

対策としては、回答時に根拠チャンクを引用させ、その引用が実際に存在するかを機械的に確認します。

### 出力段階のチェック

最後に、完成した回答が本当に出すべきものかを判定します。たとえば、同じ質問に複数回回答させて答えが一致するかを見る self-consistency や、別プロンプトで自己検証させる方法があります。

ただし、どの問題にも同じ閾値を使うのは危険です。数値問題や要素列挙問題は、普通の文章読解よりも厳しく判定すべきです。

## 4. 攻めで増やすべき能力

守りだけではスコアは上がりません。正しく答えられる問題の種類を増やす必要があります。

元文書では、`question_labels.csv` を使って valid/test の問題タイプを分類し、どの能力に投資すべきかを決めています。ここで重要なのは、勘ではなく「何問くらい効くか」で優先順位を決めていることです。

優先度が高い領域は次の通りです。

| 領域 | 何が必要か |
|---|---|
| Excel表示状態 | ハイライト、フィルター、Pivotなどを読み取る |
| Office書式 | 太字、ハイライト、コメントなどを抽出する |
| 表データ集計 | 表を pandas などで正確に計算する |
| 新旧版比較 | 変更前後の差分を意味つきで読む |
| 社内用語・略号 | 略称を正式名称や関連語に展開する |
| 契約ルール | 条件や計算式を構造化して処理する |

最初は画像やグラフ読み取りが大きな投資先に見えていました。しかし、実際に問題タイプを数えると、画像・グラフが主役の問題は少なく、ExcelやOffice書式、表集計のほうが多いことがわかりました。そのため、現在の戦略では VLM よりも構造化抽出を優先します。

## 5. 検索精度はすべての土台

RAGでは、検索に失敗するとその後の処理も失敗します。正しい資料がコンテキストに入っていない状態で、LLMだけに頼って正解することは期待できません。

検索で改善すべき点は次の通りです。

- 案件フォルダを正しく絞り込む
- BM25 とベクトル検索を組み合わせる
- 検索結果をリランキングする
- チャンクの大きさや重なりを調整する
- 文書構造やメタデータを保持する
- 社内用語や略号でクエリを拡張する

また、回答生成まで通さずに「正解の根拠チャンクが top-k に入っているか」だけを測る評価を持つと、失敗原因を切り分けやすくなります。検索で失敗しているのか、生成で失敗しているのか、確信度判定で失敗しているのかを分けて考えられるからです。

## 6. 生成精度で気をつけること

回答生成では、LLMに渡す指示とコンテキストの設計が重要です。

たとえば、数値だけを答えるべき問題で長い説明を付けると、評価側が意図しない判定をする可能性があります。逆に、根拠が必要な問題で短すぎる回答をすると、情報不足になることもあります。

基本方針は次の通りです。

- CRAGの評価基準をプロンプトに反映する
- 数値や単位を模範解答に近い粒度で出す
- 余計な文章を減らす
- コンテキストを入れすぎてノイズを増やさない
- 1000トークン以内という制約を守る

1000トークンは「そこまで書いてよい」という上限であり、「長く書くべき」という意味ではありません。むしろ、簡潔で評価しやすい回答のほうが有利なことが多いです。

## 7. 構造化抽出が重要な理由

通常のRAGはテキスト検索に強い一方で、Excelのセル色、フィルター状態、Pivot、WordやPowerPointのハイライトなどは苦手です。これらは単純にテキストを取り出すだけでは失われる情報だからです。

そこで、資料を事前に解析して、次のような形で構造化しておく必要があります。

- Excelのセル値、書式、表示状態
- Office文書の太字、ハイライト、コメント
- バージョン違いの文書ペア
- 用語集や略語の対応表
- 分析成果物やコードのレジストリ

こうした構造化データを回答パイプラインに接続できると、テキスト検索だけでは答えられなかった問題に対応できます。

## 8. 実験の進め方

スコア改善では、思いつきで機能を足すのではなく、実験として扱います。1回の実験では、変更点を1つに絞るのが基本です。

各実験では次を記録します。

1. 仮説: 何を変えると良くなると思うか
2. 期待ゲイン: 何問くらい改善しそうか
3. 実測: valid でどう変わったか
4. 採否: 採用するか、戻すか
5. 理由: なぜそう判断したか

valid は30問しかないため、1問の変化が大きく見えます。1問増えた、1問減っただけで判断せず、どのタイプの問題が改善・悪化したかを見る必要があります。

特に重要なのが flip 分析です。これは、変更前後で各問題の結果がどう変わったかを見る分析です。

- Missing から Perfect になった問題
- Incorrect から Missing になった問題
- Perfect から Incorrect に落ちた問題
- 変化しなかった問題

合計スコアだけでは、良い変化と悪い変化が打ち消し合って見えなくなることがあります。flip 分析をすると、変更の本当の影響が見えます。

## 9. 時間とコストの制約

本番では時間制限があります。100問を処理するのに時間がかかりすぎると、そもそも提出できません。

そのため、次の点も戦略に含まれます。

- パース結果やインデックスをキャッシュする
- 評価を数分で回せるようにする
- 必要なら並列処理する
- 軽量モデルと高性能モデルを使い分ける
- 1回の評価にかかるAPI費用を把握する

実験サイクルが速いほど、試せる仮説が増えます。試行回数が増えれば、スコア改善のチャンスも増えます。

## 10. 規約遵守と再現性

コンペでは、特定の質問や特定の案件名に対して個別に分岐するようなハードコードは禁止です。

たとえば、次のような実装は危険です。

- この質問文ならこの答えを返す
- このファイル名なら特別処理する
- test のラベル情報を回答生成に使う
- 人手で作った評価用ラベルを本番回答に混ぜる

許されるのは、未知の案件や未知の質問にも同じ方針で動く汎用的なロジックです。

また、本番judgeは基本的に一度きりです。ローカル評価と本番評価がずれる可能性もあるため、温度やシードを固定し、同じ入力なら同じ出力になるようにしておく必要があります。

## 11. この戦略を一言でまとめると

この戦略の中心は、「闇雲に答えるRAG」ではなく、「答えられる問題だけを確実に取りに行くRAG」を作ることです。

優先順位は次の順番です。

1. 間違いを減らすためのゲートを作る
2. 検索で正しい根拠を拾えるようにする
3. Excel、Office書式、表集計など、問題数が多い能力を追加する
4. 実験を小さく速く回し、flip分析で採否を決める
5. valid だけに過剰適合せず、本番でも通用する汎用的な改善だけを採用する

最終的な目標は、Perfect を増やすだけではありません。Incorrect をできるだけゼロに近づけながら、確信を持って答えられる範囲を広げることです。
