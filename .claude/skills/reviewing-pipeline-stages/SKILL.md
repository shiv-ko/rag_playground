# reviewing-pipeline-stages: パイプライン全体のコード実装レビュー

## Overview

このリポジトリ（RAGコンペ）のパイプラインを構成するステージごとに独立したサブエージェントを立て、
**ドキュメントではなく実装コードそのもの**を読ませてレビューさせ、指摘を重要度でトリアージして
`docs/imp/`配下にmdファイルとして保存するワークフロー。1タスクのdiffレビュー（step-review）や
GitHub PR レビュー（/review）とは別物 — こちらはリポジトリ全体・実装の妥当性を棚卸しする用途。

## When to Use

- 「全体を見直したい」「各パートの実装をレビューして」「改善点を洗い出して」と言われたとき
- フェーズの節目（本番差し替え前、コンペ提出前の総点検など）でパイプラインの健全性を確認したいとき
- step-reviewのような1コミット単位のレビューでは拾えない、ステージ内の設計・実装の妥当性を見たいとき

## ワークフロー

1. **全体像を把握する** — `vault.md`→`docs/plan/`の最新next-steps→`.claude/skills/architecture.md`の順に読み、
   現在のパイプライン構成（本番差し替え済みの箇所・スタブのままの箇所）を掴む。
2. **ステージを列挙する** — `ls src/`でトップレベルディレクトリを再確認する（下記は執筆時点のリストで、
   ディレクトリ構成が変わっていたら実際の`src/`を正とする）:

   | ステージ | ディレクトリ | 役割 |
   |---|---|---|
   | 前処理・パース | `src/parsers/` | 拡張子振り分け・チャンキング・PDF/Office/画像パース |
   | インデックス | `src/indexer/` | BM25/TF-IDF、ベクトルストア |
   | 検索 | `src/retriever/` | 案件スコープ検索、クエリ拡張、構造化コンテキスト |
   | 生成 | `src/generator/` | 回答生成、引用チェック、confidence gate |
   | 評価 | `src/evaluator/` | ジャッジ、メトリクス、トリアージ |
   | 構造化データ | `src/structured/` | artifact store |
   | オーケストレーション | `src/orchestrator/` | pipeline本体、answer stabilizer |
   | 共通基盤 | `src/utils/` | ログ・パスキャッシュ・質問分類等 |

3. **ステージごとに1エージェントを並列dispatch** — Agentツールを1メッセージ内で複数回呼び、独立実行する。
   - `subagent_type: "general-purpose"`（forkではなく新規エージェント。会話の先入観なしでコードだけを読ませたいため）
   - モデルはCLAUDE.mdの方針どおり難易度で選ぶ: **parsers/indexer/retriever/generator/evaluator/orchestrator はSonnet 5**、
     **utils/structured のような薄いユーティリティ層はHaiku**。ここに載っていないステージが増えていたら
     「そのステージのバグが誤答に直結するか」で決める（直結する→Sonnet、しない→Haiku）
   - プロンプトは下記テンプレートを自己完結させて渡す（親はdiffやコードを貼らず、エージェント自身に読ませる）

4. **各エージェントの結果を`docs/imp/<stage>_review_YYYYMMDD.md`に保存** — 出力テンプレートに従う。
5. **全ステージ分を横断して優先度順に並べた`docs/imp/summary_YYYYMMDD.md`を1本作る** — 各ステージ報告から
   重大(P0)指摘を中心に抜き出し、対応順の推奨リストにする。個別ファイルへのリンクを添える。
6. `vault.md`のディレクトリ規約表に`docs/imp/`の行がなければ1行追加する（保存ルールの索引を最新に保つ）。

## エージェントへの依頼テンプレート

```
あなたは /Users/shiv/P/rag_comp（RAGコンペ）の <ステージ名> パートのコードレビュアーです。

【対象】<src/xxx/ 配下の実ファイルパスを列挙>
【禁止】docs/配下のmdやREADMEの記述を鵜呑みにしない。必ず実装コード（と対応する tests/test_xxx.py）を
    自分で読んで判断すること。テストが実データの形式（列名ゆれ・日本語NFC/NFD・番号接頭辞等）を
    反映しているかも確認する。
【確認観点】
1. 正しさ: 分岐の排他ミス、デッドコード、境界条件、例外処理の握りつぶし
2. 実データ前提の欠落: 日本語文字列比較のNFC/NFD正規化、列名ゆれ、エンコーディング、空/欠損値
3. 二重管理・重複ロジック: 同じ処理が複数ファイルに存在し片方だけ更新されている
4. 効率: 明らかに無駄な再計算・O(n^2)化・不要なI/O
5. 競技規約: 特定案件名・ファイル名・正解のハードコード、question_labels.csv（人手ラベル）の
   回答生成パスへの混入
6. このステージ固有の改善余地（該当ファイルを踏まえて具体的に）

【出力形式】重要度でトリアージし、各指摘は file:line + 何が起きるか（具体的な入力例）を書くこと。
- P0（重大 = 誤答/規約違反/クラッシュにつながる）
- P1（中 = 実データで問題になりうる/保守性を損なう）
- P2（軽微 = 効率・可読性・nice-to-have）
根拠のない一般論（「もっとテストを増やすべき」等）は書かない。問題なければそのカテゴリは「なし」と書く。
```

## 出力テンプレート（`docs/imp/<stage>_review_YYYYMMDD.md`）

```markdown
# <ステージ名> 実装レビュー（YYYY-MM-DD）

対象: src/<stage>/ 配下（ファイル一覧）
参照コミット: <git rev-parse --short HEAD>

## P0（重大）
- `path/to/file.py:123` — 指摘内容。壊れる具体的シナリオ。

## P1（中）
- ...

## P2（軽微）
- ...
```

## Quick Reference

| やりたいこと | 使うもの |
|---|---|
| 1コミット分のdiffだけレビュー | step-review スキル |
| GitHub PRレビュー | /review |
| リポジトリ全体をパート別に棚卸し | このスキル |
| パイプライン構成を確認したい | architecture スキル |

## Common Mistakes

- 親エージェントがコードを読んでレビュー内容を要約し、それをサブエージェントに丸投げする
  → 各サブエージェントは自分で`src/`と`tests/`を読むこと。ドキュメント伝聞のレビューは実装との乖離を見逃す。
- 全ステージを1エージェントに一括で投げる → 文脈が薄まり、各ステージの具体的な指摘が浅くなる。
  ステージごとに独立dispatchする。
- 指摘に file:line や具体的な壊れ方がない一般論を採用する → 出力テンプレートのP0/P1/P2それぞれで
  具体性のない指摘は却下し、再レビューさせる。
